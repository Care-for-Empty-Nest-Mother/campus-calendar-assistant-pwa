# 校历小助手：Android 与 iOS 跨平台适配问题及经验总结报告

> 项目：校历小助手  
> 最终形态：Android APK 1.6 + GitHub Pages PWA + iOS 快捷指令桥接  
> 适用读者：后续需要同时适配 Android、iOS、PWA、WebView、系统日历或系统提醒的项目开发者  
> 结论先行：跨平台适配的核心不是“把同一份页面搬到两个系统”，而是把“网页能力、原生能力、系统权限、文件与剪贴板交接”拆成清晰、可验证的桥接层。

## 1. 项目背景

校历小助手最初是一个纯网页课表与校历工具，随后逐步扩展为：

- Android：Capacitor 打包 APK，使用原生 WebView、系统日历、系统通知和精确闹钟。
- iOS：不采用 App Store 上架路线，使用 GitHub Pages PWA + iOS 快捷指令补足 Safari 无法直接完成的能力。
- 数据来源：西安石油大学研究生教务系统，页面为 HTTP，课表位于 iframe/Frame 内，单元格存在 rowspan、同一格多课程等情况。
- 最终目标：用户不需要电脑、不需要 Mac、不需要 Apple Developer 付费账号，也能在 Android 和 iOS 上完成课表提取、课表查看、系统日历同步和提醒。

## 2. 最终架构

```text
┌──────────────────────────────────────────────┐
│              Web 核心（单页应用）              │
│ index.html / data.js / manifest.json / sw.js │
│ 课表解析、校历、考试、待办、主题、本地存储       │
└───────────────┬──────────────────┬───────────┘
                │                  │
        Android 原生桥          iOS 快捷指令桥
                │                  │
   WebView + 系统日历/通知     Safari PWA + 快捷指令
   APK / Capacitor            剪贴板 + 系统日历写入
```

### 2.1 各平台能力分工

| 能力 | Android APK | iOS PWA |
|---|---|---|
| 打开教务系统并保持登录 | 原生 WebView | Safari 新标签页 |
| 提取课表 | 原生 WebView 注入脚本 | Safari 分享菜单运行快捷指令 |
| 解析课表 | 网页端 JavaScript | 网页端 JavaScript |
| 系统日历 | Capacitor 原生插件直接写入 | 快捷指令读取剪贴板后写入 |
| 课前提醒 | 原生日历/通知/精确闹钟 | 系统日历事件提醒 |
| 后台能力 | 系统通知可后台显示 | 主要依赖系统日历/提醒 |
| 安装方式 | APK 文件安装 | Safari 添加到主屏幕 |
| 更新方式 | 重新构建 APK 覆盖安装 | GitHub Pages 自动更新，必要时刷新缓存 |
| Safari → 主屏幕数据迁移 | 不涉及 | 用户点击复制迁移数据，再由主屏幕 Web App 恢复 |

## 3. Android 端问题与修复经验

### 3.1 HTTP 教务系统导致 `ERR_CLEARTEXT_NOT_PERMITTED`

**现象**

APK 在本机开发环境可打开教务系统，但安装到其他手机后，登录页报：

```text
net::ERR_CLEARTEXT_NOT_PERMITTED
```

**原因**

教务系统地址是 `http://`，Android 9 及以上默认禁止应用明文 HTTP 流量。开发时某些 WebView 配置、浏览器缓存或系统版本可能掩盖问题，但换手机后必须显式允许明文流量。

**修复**

`AndroidManifest.xml` 中加入：

```xml
<application
    android:usesCleartextTraffic="true"
    android:networkSecurityConfig="@xml/network_security_config">
```

同时保留网络权限：

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
```

**经验**

- 只做 Web 页面调试时，浏览器能访问 HTTP 不代表 APK WebView 能访问。
- 必须把“网络权限、明文流量、WebView 域名策略”作为独立验收项。
- 如果生产环境可控，优先使用 HTTPS；教育网/校方旧系统无法改 HTTPS 时，才使用按域名放行的网络配置，避免全应用无差别放开。

### 3.2 登录状态、Cookie 和跨域提取

**现象**

网页直接 `fetch` 教务系统会受 CORS、Cookie、会话和重定向限制，无法读取登录后的课表。

**修复思路**

- 不在普通网页里直接请求受保护的教务页面。
- Android 使用原生 `ExtractorActivity` 打开登录页，让 WebView 自己维护 Cookie 和统一身份认证会话。
- 登录成功后，仅在当前 WebView 页面注入提取脚本。
- 提取脚本读取 DOM 和直接 Frame，不依赖 CORS 请求。

**经验**

浏览器安全策略不是“可以用后台代码绕过”的障碍。正确方案是：

1. 在用户可见的原生 WebView 中完成登录；
2. 在同一个页面上下文中执行 DOM 提取；
3. 把结果以结构化字符串返回业务层。

### 3.3 课表位于 iframe，且存在 rowspan 与同格多课程

西安石油大学教务系统的课表通常位于 `#mainFrame` 或类似的 Frame 中，表头包含星期，单元格可能跨行合并，同一格还可能包含两门不同课程。

**解决原则**

- 先找 `table#kb`、`table.curriculum` 或评分最高的课程表；
- 允许穿透一层直接 Frame，不做无限递归；
- 将 rowspan 展开为统一的二维网格；
- 单元格文本按换行拆分成多门课程；
- 课程如果名称、时间、节次、星期、周次、教室、教师任一不同，就保留为不同课程；
- 只返回原始表格结构，不在提取脚本里做复杂业务判断。

**经验**

不要把“提取”和“导入”混在同一层。推荐协议：

```text
提取层：表格 DOM -> 结构化 rows
解析层：rows -> 课程对象
导入层：课程对象 -> 去重、校对、存储、渲染
```

这样 Android 原生提取、iOS 快捷指令提取和网页粘贴识别可以复用同一个解析器。

### 3.4 课程解析的教师、教室、周次误判

**现象**

课程文本类似：

```text
数理统计（鄠邑4班）3-14周 董晓亮鄠邑校区博思楼B125
```

不同教师名、校区名、楼名和教室号没有统一分隔符，简单按空格或固定正则拆分会把教室误当教师，或把教师和地点合并。

**修复经验**

- 支持标签式字段和紧凑文本两套解析路径；
- 优先识别 `任课教师:`、`教师:`、`老师:` 等明确标签；
- 对无标签文本，先识别周次、节次、星期和教室模式，再从剩余文本中提取教师；
- 同一格多课程时逐条解析，不把合并文本当成一门课；
- 建立覆盖真实样本的回归测试，至少包含：
  - 普通课程；
  - 同一格两门课；
  - 单双周；
  - rowspan 跨行；
  - 教师名与地点粘连；
  - 同名课程不同教师/教室/周次。

### 3.5 Android 权限与后台提醒

项目使用了以下权限：

| 权限 | 用途 |
|---|---|
| `READ_CALENDAR` / `WRITE_CALENDAR` | 写入课表、考试、待办和提醒 |
| `POST_NOTIFICATIONS` | Android 13+ 通知权限 |
| `SCHEDULE_EXACT_ALARM` | Android 12+ 精确上课提醒 |
| `RECEIVE_BOOT_COMPLETED` | 重启后恢复提醒排程 |

**经验**

- 权限必须在真实系统设置中验证，而不是只在开发机确认。
- Android 13+ 的通知权限是运行时权限；Android 12+ 的精确闹钟可能还需要用户到系统设置允许。
- App 内开关、系统权限和实际排程是三件事，三者都成功才算提醒生效。
- 如果只排未来 7 天，用户需要周期性打开 App 续排，这是 Android 后台限制下的现实取舍。

### 3.6 APK 调试、USB 和热载入

**过程**

- 使用 USB 调试连接手机；
- 通过端口反向映射让手机浏览器访问电脑本机预览页；
- 使用 Capacitor 热载入安装开发版 App，手机端可实时看到页面修改。

**经验**

- 先保证“手机浏览器能打开”再排查 App，可以快速区分网络问题和打包问题。
- 调试开发版和最终 APK 要分别验证；开发机环境正常不代表 APK 正常。
- 真机调试能让明文 HTTP、Cookie、WebView、文件下载和系统权限问题提前暴露。

### 3.7 APK 版本与覆盖安装

- `versionCode` 和 `versionName` 必须随发布递增。
- 同一包名、同一签名密钥才能稳定覆盖安装并保留本地数据。
- 改完网页后先同步 Web 资产，再重新构建 APK：

```bash
npm run cap:sync
npx cap copy android
```

随后使用 Android Studio 或 Gradle 构建 APK。

**经验**

APK 发布后，网页源文件、`www/` 资产、Android 工程和 APK 是四层不同产物。只修改根目录页面而不执行同步，会导致 APK 看起来“没有更新”。

## 4. iOS 端问题与修复经验

### 4.1 没有 Mac、没有 Apple ID 时的路线选择

iOS 真机安装原生 App 必须有签名环境；不登录 Apple ID 只能运行模拟器或生成不可直接安装的未签名产物。

最终采用的路线是：

- GitHub Pages 托管 PWA；
- Safari“添加到主屏幕”；
- 使用 iOS“快捷指令”补足网页无法访问的能力；
- 保留 Capacitor iOS 工程，方便未来有 Mac 时再构建原生版本。

**为什么不直接接入微信小程序或模拟 Mac**

项目也评估过微信小程序、云打包和 Mac 模拟环境。微信小程序需要额外的平台账号、审核和域名/网络白名单配置；本项目的教务系统是校园内网 HTTP 地址，登录态和跨域限制复杂，迁移成本并不会因为“跨平台”而消失。模拟 Mac 只能解决构建环境问题，不能替代真实 iOS 设备上的权限、文件导入、快捷指令和日历行为验证。最终选择 PWA + Shortcuts，是因为它更符合“不上架、低成本、用户可自行安装”的目标。

**经验**

“原生 App”不是唯一方案。对校园工具类应用，如果核心能力是数据查看、轻量交互和系统日历/提醒，PWA + Shortcuts 可以在不上架、不购买开发者账号的情况下覆盖主要场景，但必须明确哪些能力无法做到完全后台化。

### 4.2 Safari 不能直接跨站注入教务系统页面

普通 PWA、网页脚本或书签不能像 Android WebView 一样稳定地读取登录后的跨站页面。

**解决方式**

- 使用“在网页上运行 JavaScript”的系统快捷指令；
- 快捷指令由用户从 Safari 分享菜单主动触发；
- 只在当前页和一层直接 Frame 上执行；
- 运行前必须打开“学生课表查询”并等待表格渲染。

**经验**

iOS 的安全模型不允许“完全静默的跨站抓取”。合理做法是把用户操作设计成一次明确的分享动作，后续解析和导入全部自动化。

### 4.3 `shortcuts://import-shortcut` 安装无效

**现象**

iPad 点击安装链接后显示“无效 URL”。

**原因**

直接把 `shortcuts://import-shortcut?...` 拼成 URL，在当前 iPadOS/Safari 环境中不可靠。不同版本的 Shortcuts URL Scheme 支持并不一致。

**最终方案：v9 同款内置 Blob 下载**

1. 把签名后的 `.shortcut` 文件 Base64 嵌入安装页；
2. 页面加载后还原为 `Uint8Array`；
3. 校验前 4 字节为 `AEA1`；
4. 创建：

```js
new Blob([bytes], { type: 'application/x-apple-shortcut' })
```

5. 通过 `URL.createObjectURL()` 赋给 `<a download>`;
6. 用户点击后选择“存储到文件”；
7. 在“文件”App 中点击 `.shortcut`，选择“添加快捷指令”。

**经验**

不要假设系统 URL Scheme 在所有 iOS/iPadOS 版本上一致。对文件导入类流程，优先采用浏览器原生 Blob/Download，把文件交给“文件”App，再由系统决定如何导入。

### 4.4 下载下来的是 HTML 或乱码

**现象**

点击 `.shortcut` 后打开的是 HTML，或者文件无法被 Shortcuts 识别。

**原因**

- Service Worker 把 `.shortcut` 请求回退成了 `index.html`；
- 服务器 MIME 类型不正确；
- 旧版本使用普通链接而不是签名文件；
- GitHub Pages 缓存或 Safari 页面缓存。

**修复**

- Service Worker 明确排除 `.shortcut` 和安装页导航；
- 安装页使用 Base64 + Blob 生成文件；
- 签名文件校验 `AEA1` 文件头；
- 统一使用带版本查询参数的在线链接；
- 主页面、安装页、构建脚本、签名文件和 Pages 部署文件做自动一致性校验。

**经验**

静态 PWA 对下载文件要特别小心。任何“导航回退到 index.html”的缓存策略，都可能把二进制安装包变成 HTML。

### 4.5 快捷指令结果无法回到课表页面

**现象**

快捷指令执行成功，但返回网页后看不到“确认导入”，或者提示“当前没有待处理的快捷指令结果”。

**原因**

- Safari、主屏幕 PWA 和快捷指令之间不一定共享 `localStorage`；
- 把完整课表放进 URL 会被 iOS 截断；
- 打开新顶层页面可能让旧上下文中的结果丢失；
- 递归跳转或多个页面层级会增加失败概率。

**最终方案**

- 快捷指令把提取结果复制到系统剪贴板；
- 只打开一个很短的 URL，例如 `?shortcut=1&clip=1&v=9`；
- PWA 中增加独立的“快捷指令提取结果”页面；
- 页面优先自动读取剪贴板，失败时显示“读取剪贴板”和手动粘贴兜底；
- 不再把完整课表塞进 URL，也不递归打开多个页面。

**经验**

跨应用数据交接要采用“单一事实来源 + 单一短入口”：

- 大对象：剪贴板、文件或应用内暂存；
- 轻量信号：短 URL；
- 失败兜底：用户可手动粘贴。

### 4.6 iOS 快捷指令脚本环境差异

**现象**

曾出现：

```text
Can't find variable: HTML_RX
```

旧脚本还出现过提取结果为空、共享上下文不正确、运行时变量未定义等问题。

**原因**

“在网页上运行 JavaScript”运行环境和普通浏览器控制台不完全一致，脚本不应依赖外部常量、页面预先注入的全局变量或跨运行状态。

**修复经验**

- 脚本必须自包含；
- 避免依赖复杂全局正则变量；
- 使用 DOM API 查找表格和 Frame；
- 只处理直接 Frame，不递归；
- 所有成功/失败都通过统一前缀返回；
- 回调函数必须存在并稳定调用；
- 脚本执行后只返回可序列化字符串。

**协议示例**

```text
XPU_COURSE_V9:{...JSON...}
XPU_COURSE_V9_ERROR:错误原因
```

### 4.7 列表索引是 1-based

**现象**

日历快捷指令运行时报：

```text
你要求的是第 0 项，但第一项位于索引 1
```

**原因**

Shortcuts 的 `Get Item from List` 使用 1 开始的索引，而生成脚本最初按程序习惯传入了 0、1、2。

**修复**

所有字段索引统一改为：

```text
1, 2, 3, 4, 5, 6, 7, 8, 9
```

**经验**

不要用普通编程语言的数组索引习惯推断快捷指令参数。每个系统动作的索引语义必须单独确认。

### 4.8 快捷指令名称必须完全匹配

**现象**

快捷指令已经出现在 Shortcuts 列表，但网页启动时报“未找到快捷指令”。

**原因**

网页使用 `shortcuts://run-shortcut?name=...` 精确查找显示名称。导入文件时的文件名、内部名称和网页启动名可能不一致。

**最终规则**

- 构建器名称、签名文件名、安装页下载名、网页启动名、Pages 部署名必须一致；
- 当前日历同步使用 ASCII 名称：

```text
calendar-sync-v2.2
```

- `tools/check-shortcut-sync.js` 自动校验：
  - 网页 runner；
  - 快捷指令构建器名称；
  - 安装页下载文件；
  - 签名文件是否存在且为 `AEA1`；
  - GitHub Pages 是否复制了对应文件。

**经验**

名称是跨系统集成协议的一部分。所有名称都应集中配置，并加自动校验，而不是依赖人工记忆。

### 4.9 每次添加课程都弹出“添加”确认

**现象**

日历快捷指令能打开，但每写入一门课程都要手动点击一次“添加”。

**原因**

`Add New Event` 动作的现代参数是：

```text
ShowWhenRun
```

旧构建脚本使用了不被识别的 `WFCalendarItemShowComposer`、`ShowComposeSheet` 等参数，或被默认值覆盖，导致每次写入都弹出编辑/确认界面。

**修复**

对每个写入动作设置：

```text
ShowWhenRun = false
```

**经验**

- 参数名必须与当前 iOS Shortcuts 版本的 action schema 匹配；
- 不要只凭旧版本论坛示例或名字猜测；
- 对批量写入动作必须专门验证“是否每项都弹 UI”。

### 4.10 日历同步必须先清除同类旧日程

如果直接重复写入，日历中会出现大量重复课程。最终方案是：

1. 用户选择日程类别和日期范围；
2. 快捷指令先用 Notes 中的标记和日期范围筛选本应用写入的旧事件；
3. 删除同类范围内的旧事件；
4. 再写入新的课程、考试、上课提醒和待办；
5. 不同类别互不影响。

**经验**

同步功能必须支持“再次运行”而不产生不可控重复。推荐采用：

- 明确的应用标记；
- 类别字段；
- 日期范围；
- 先清除后写入；
- 清除范围尽量小。

### 4.11 Safari 标签页与主屏幕版的数据存储隔离

**现象**

用户已经在 Safari 的校历小助手中成功导入课表，但将同一网址“添加到主屏幕”后，主屏幕版仍显示“尚未导入课表”或“尚未使用”的空界面。

**根因**

iOS 会把 Safari 普通标签页和“添加到主屏幕”后的独立 Web App 视为不同的 WebKit 使用环境。即使二者：

- 域名相同；
- `origin` 相同；
- `manifest.json`、`scope` 和文件版本相同；
- Service Worker 缓存相同；

也不能保证共享 `localStorage`、`IndexedDB`、Cookie/会话或页面内存。主屏幕 App 拥有自己的数据容器，因此 Safari 中写入的课表不会自动出现在主屏幕版中。

这不是页面解析器或课表保存失败，而是 iOS 的存储隔离行为。

**不可行的错误思路**

- 不能只依赖“同一网址就应该共享 localStorage”的假设；
- 不能通过打开一个新窗口、新标签页或隐藏 iframe 读取另一个 Web App 容器的数据；
- 不适合把完整课表 JSON 长期放在 URL Hash 中，课表数据变大后可能触发 URL 长度、分享链接和系统截断问题；
- Service Worker 只能缓存资源，不能充当两个存储容器之间的实时数据库；
- 不应该在用户无操作时静默读取剪贴板，iOS 会要求用户激活或明确授权。

**最终采用的方案：显式剪贴板迁移协议**

页面新增一条一次性、带版本号的迁移通道：

```text
XPU_APP_TRANSFER_V1:{JSON}
```

迁移快照包含：

- 课表 `store` 与课程数组；
- 考试 `EXAMS`；
- 待办 `TODOS`；
- 设置 `settings`（校区、主题、提醒等）；
- 尚未处理的快捷指令结果（如有）。

操作流程：

1. 在 Safari 的课表页检测到已有课表时，显示“让主屏幕版显示已导入课表”；
2. 用户点击 **复制课表到主屏幕版**，网页通过 `navigator.clipboard.writeText()` 写入迁移数据；
3. 在独立主屏幕版中，如果本容器没有课表，页面显示“恢复 Safari 中已导入的课表”；
4. 页面尝试自动读取剪贴板；如果 iOS 因用户激活或隐私策略拒绝，用户点击 **从 Safari 恢复课表**；
5. 恢复成功后同时写入课程、考试、待办和设置，并移除迁移提示。

复制失败时保留文本框手动复制；自动读取失败时保留长按粘贴和“解析粘贴内容”按钮，形成双层兜底。

**实现与验证要点**

- 迁移数据必须带 `app` 和 `version` 字段，恢复前校验，避免误解析其他剪贴板内容；
- 恢复动作必须对课程、考试、待办、设置分别落盘到当前容器的 `localStorage`；
- 更新 Service Worker 缓存版本，避免用户拿到旧页面；
- 用 iOS User-Agent 和 `navigator.standalone` 分别模拟 Safari 与主屏幕环境；
- 测试步骤应覆盖“Safari 有课表 → 复制 → 主屏幕空存储 → 恢复 → 课程渲染”的完整链路；
- 同时验证复制失败、剪贴板读取失败和手动粘贴路径，不能只测自动成功路径。

**经验**

1. **同一 `origin` 不等于同一数据容器。** iOS PWA、Safari 标签页和普通网页必须按独立存储环境设计。
2. **跨容器迁移动作必须显式且可观察。** 用户知道自己在复制什么、恢复到哪个版本，失败时能看到下一步。
3. **大对象交接优先使用剪贴板或文件，小信号才使用 URL。** 这比把完整课表塞进链接更稳定。
4. **用户激活是 iOS 权限模型的一部分。** 首次读取剪贴板需要允许或点击触发，必须准备手动粘贴兜底。
5. **迁移要保留完整业务状态。** 只搬课程而漏掉考试、待办和设置，会让用户误以为恢复成功但数据并不完整。
6. **上线前必须增加缓存版本和旧页面刷新说明。** 数据代码已更新但用户仍加载旧页面，表现会像“修复无效”。

## 5. 课表解析与数据协议的通用经验

### 5.1 大节与节次统一

教务系统中的“上午1、上午2、下午5”等显示方式与课表的大节划分不完全一致。最终采用“大节”作为课程格子的基础单位，解析时统一映射到 1 到 10 的节次范围。

**经验**

- 原始文本不要直接作为内部节次；
- 先建立显示节次到内部大节的映射；
- 导入和快捷指令解析共用同一套映射。

### 5.2 保留课程身份，而不是只按名称合并

同一门课程可能因教师、教室、周次或节次不同而属于不同课程。最终去重时使用组合身份：

```text
名称 + 星期 + 开始节次 + 结束节次 + 周次 + 教室 + 教师
```

**经验**

只按课程名称合并会丢课；只按整行合并会丢同格双课。最稳妥的是先解析成标准课程对象，再按完整身份去重。

### 5.3 结果预览与人工确认

快捷指令和网页导入都不直接覆盖现有课表，而是先进入预览页：

- 可选择课程；
- 可修正周次、节次、教室和教师；
- 可选择替换或追加；
- 确认后才进入正式课表。

**经验**

自动提取不可能覆盖所有教务页面变体，保留“校对后导入”能显著降低误识别造成的破坏。

### 5.4 产品交互问题与工程经验

除了平台适配，本项目还修复了若干典型的交互和状态同步问题，这些问题在其他跨平台项目中也常见：

| 问题 | 根因 | 经验 |
|---|---|---|
| 课表作息校区点击无反应 | 页面局部重绘后事件绑定失效，或状态改变没有触发重渲染 | 事件绑定要稳定；每次状态变化后统一重绘；关键开关加入自动化点击回归测试 |
| 校历月份选择与下方日历表头不同步 | 月份状态存在多个来源 | 只保留一个月份状态源，选择器和日历表头都从同一状态渲染 |
| 课表课程格子没有占满大节区域 | 固定高度和跨行计算不匹配 | 表格单元格使用 rowspan 或动态高度，课程卡片填满容器并保持可读性 |
| 明日课程展示过长 | 普通横向列表在窄屏上挤压或换行 | 使用横向滚动容器，固定卡片宽度，保留滑动提示 |
| 上课地点提醒不够醒目 | 教室、教学楼和班级号在合并文本中权重一致 | 解析后拆分地点字段，对教学楼和班级号单独加粗标红 |
| 校历事项与课程提醒语义混淆 | “校历事项”被当作单一提醒类型 | 将其拆分为课程、考试、上课提醒、待办等可独立同步的类别 |
| 同步范围互相覆盖 | 清除逻辑缺少类别和日期边界 | 每个类别保留独立标记，按类别与日期范围清除，保证彼此独立 |
| 一次同步包含多种内容时顺序混乱 | 生成、复制、清除、写入混在一个步骤中 | 先结构化生成，再复制交接，再由平台端执行清除和写入 |

这些问题的共同教训是：跨平台项目不能只验证“数据是否能显示”，还要验证状态更新、局部重绘、点击事件、滚动布局、同步幂等性和失败后的恢复路径。

## 6. PWA 与部署问题

### 6.1 GitHub Pages 适合本项目

- 电脑关机不影响线上访问；
- HTTPS 满足 PWA 和 Service Worker 要求；
- 修改后通过 GitHub Actions 自动部署；
- 多设备共享同一在线地址。

### 6.2 Service Worker 缓存策略

本项目采用：

- 页面导航：网络优先，失败时回退缓存；
- 普通静态资源：缓存优先；
- `.shortcut`、安装页和导航到大文件：交给浏览器原生处理，绝不回退 `index.html`。

**经验**

缓存策略必须按资源类型区分。把所有导航都回退到入口 HTML，会破坏下载文件和外部应用跳转。

### 6.3 页面更新与缓存

- 使用 `?v=...` 或等价查询参数刷新；
- 修改安装页后重新打开带新参数的 URL；
- 用户看到旧界面时，先关闭旧标签页再从新链接进入；
- 不要把 GitHub Pages 已部署和浏览器本地缓存混为一谈。

## 7. 项目最终沉淀的工程原则

1. **减少操作步骤**：每增加一步手动确认，就增加一次用户失败的机会。
2. **平台能力分层**：Web 负责数据和界面，原生/快捷指令只负责平台桥接。
3. **双通道交接**：大对象走剪贴板或文件，小信号走短 URL。
4. **版本即协议**：快捷指令名称、文件名、内置版本和网页启动名必须同步。
5. **脚本自包含**：跨系统执行的 JavaScript 不依赖外部全局变量。
6. **优先 DOM，少用大正则**：课表结构变化时 DOM 方案更可调试。
7. **先预览后写入**：提取结果和系统日历写入都应可校对、可清除、可重复运行。
8. **权限不能绕过**：脚本权限、日历权限、剪贴板权限必须在首次使用时明确引导。
9. **保留降级路径**：快捷指令失效时保留手动粘贴、JSON 和 ICS 兜底。
10. **自动校验优先于人工记忆**：名称、文件、部署路径和版本一致性必须由脚本检查。
11. **真机验收**：开发机、模拟器、本机浏览器通过，不等于其他手机或其他 iPad 通过。
12. **记录平台限制**：明确哪些能力只能在 Android 原生、哪些依赖 iOS 系统日历或快捷指令。
13. **把存储容器当作独立环境**：Safari、主屏幕 PWA、标准网页和 APK WebView 不能假设共享 `localStorage` 或会话，跨容器数据必须设计显式迁移协议。

## 9. 已知边界与未来建议

- iOS PWA 仍然不能像 Android APK 一样完全后台运行和静默访问任意网页。
- iOS 快捷指令首次安装、脚本权限和日历权限仍需要用户手动确认一次。
- 剪贴板写入和读取可能受系统隐私提示影响，需要保留手动粘贴入口。
- Safari 标签页与主屏幕 PWA 的存储容器彼此隔离，无法实现无用户操作的静默同步；首次迁移必须保留明确的复制/恢复步骤。
- 如果后续需要原生 iOS 推送、复杂后台同步或 App Store 分发，必须在 macOS + Xcode 上完成签名和构建。
- 如果教务系统页面结构变化，优先更新提取脚本和解析器，不要把兼容逻辑写死在展示层。
- 如果未来支持更多学校或更多教务系统，建议把“页面适配器”和“课程解析器”拆成插件化模块。

## 10. 结论

校历小助手最终同时覆盖了 Android 和 iOS，但两条路线并不相同：Android 依靠 Capacitor 原生层获得完整系统能力，iOS 依靠 PWA + 快捷指令安全、低门槛地补齐关键功能。

本项目最重要的经验是：跨平台适配要围绕“能力桥接、数据协议、权限边界、版本一致性、降级路径”设计，而不是简单地追求同一套代码在所有设备上表现完全相同。只要把这些桥接关系明确下来，Android 端、iOS 端和网页端就可以在各自能力边界内稳定共存。
